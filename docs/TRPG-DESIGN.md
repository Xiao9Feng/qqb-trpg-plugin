# 跑团笔记本（TRPG 插件）设计稿

> 目标：让鱼鱼**当 PL（玩家）**参加 CoC 跑团，靠外置结构化档案记住线索、人物、进度。**KP 是真人**，骰子用群里现成的骰娘。
> 状态：**已实现（2026-10-27）**。存储层 `src/trpg/store.mjs`、工具面 `src/trpg/mcp-server.mjs`（13 个工具），MCP 名 `trpg`（工具前缀 `mcp__trpg__`）。实现记录见文末。原设计写于 2026-10-26。

---

## 零、前提（决定了整个设计）

| 前提 | 对设计的影响 |
|---|---|
| **鱼鱼只当 PL，KP 是真人** | 不需要 `secrets/` 目录、不需要 KP 模式、不做「它知道真相但不能说」的表演 |
| **大约 200 条上下文就手动重启** | `recap` 不再是「生成摘要」，而是**「重启后一键回到现场」**——这是全插件最关键的工具 |
| **骰娘已有真随机，不用鱼鱼掷** | 删掉 `trpg_roll` / `trpg_san_check`。它负责记账，不负责运气 |
| **骰子只是短线状态判断（2026-10-26 确认）** | 骰点**本身不入档案**，用完即弃。只记它的**后果**：SAN/HP 变化、线索拿到没、时间线里的结论。所以**不需要 `dice.log`，也不需要 `trpg_dice_record`** |
| **骰点由 KP 解读，鱼鱼只等结果（再确认）** | 鱼鱼**绝不自己算成败**（看到 `.ra侦查 → 78` 不能自己比 65 判失败）。等 KP 说「你成功了/失败了」再落档。这条必须写进 preset，否则模型会抢答，抢答一旦和 KP 不一致整个团就乱套 |

## 一、为什么不能用现有记忆系统

| 现有系统 | 为什么不合适 |
|---|---|
| 三层记忆（`state/memory`） | 它记的是「群友是什么人」，是**日常人设**。跑团档案是**虚构世界的事实**，混进去会污染人设（鱼鱼会以为「阿蓝」真在邪教里） |
| 会话内 `activeTopics` | 会话重置就没了，而跑团要跨几周 |
| DSH 上下文压缩 | 压缩会丢细节，而跑团恰恰靠细节破案 |

结论：**独立一套，独立目录，独立工具面**。

## 二、核心数据结构

每个团一个目录，全部 markdown + json（人可读、可导出、能 git）：

```
state/trpg/<模组名>/
├── campaign.json          团信息：模组、KP、玩家、开始时间、当前场景
├── clues.md               线索卡（★ 核心）
├── npcs.md                NPC 与关系网
├── timeline.md            事件时间线（只记结论，不记骰点）
└── chars/
    └── <角色名>.json      调查员卡：属性/技能/物品/HP/SAN 当前值
```

### 线索卡（最关键的一张表）

CoC 的难点不是「记不住线索」，而是**假线索**。NPC 会撒说，玩家会误解。所以每条带三样：

```json
{
  "id": "clue-003",
  "text": "酒保说地下室那晚有人搬箱子",
  "source": "NPC:酒保约翰",
  "verified": false,
  "confidence": "medium",
  "foundAt": "第一夜 · 酒馆",
  "related": ["npc:酒保约翰", "scene:酒馆地下室"],
  "status": "active"
}
```

> **为什么要 `verified`**：模型很喜欢把 NPC 的台词当成事实记下来，然后拿它去推理，越推越离谱。强制分开「谁说的」和「是不是真的」，能挡掉一大半幻觉。

### 角色卡（CoC 7 版）

```json
{
  "name": "鱼鱼",
  "occupation": "记者",
  "attributes": { "STR": 45, "CON": 60, "SIZ": 50, "DEX": 70, "APP": 65, "INT": 75, "POW": 55, "EDU": 70 },
  "derived": { "HP": 11, "MP": 11, "SAN": 55, "MOV": 8 },
  "skills": { "侦查": 65, "图书馆使用": 60, "心理学": 45, "闪避": 35 },
  "items": ["相机", "笔记本", "手电筒"],
  "current": { "HP": 11, "MP": 11, "SAN": 52, "status": ["轻微擦伤"] }
}
```

## 三、工具清单（缩水后只剩 7 个）

| 工具 | 作用 | 关键点 |
|---|---|---|
| `trpg_new` | 开团/加入团 | 模组名、KP、角色名 |
| `trpg_state` | ★ **重启后一键回现场** | 当前场景 + 活跃线索 + 角色状态 + 最近事件，控制在 800 字内 |
| `trpg_clue_add` | 记一条线索 | **强制填 source**，默认 verified=false |
| `trpg_clue_find` | 按关键词/人物/场景查线索 | 返回时附带 verified 状态 |
| `trpg_clue_mark` | 标记「证实 / 推翻 / 存疑」 | 长团最容易漏、但最有价值的一步 |
| `trpg_char_show` / `trpg_char_patch` | 读/改角色卡（HP/SAN/物品） | 只允许增量改动，附原因 |
| `trpg_timeline_add` | 记事件 | 带游戏内时间 |
| `trpg_npc_add` / `trpg_npc_get` | NPC 与关系 | 含「对他人的态度」 |

> 不做：`trpg_roll`、`trpg_san_check`（骰娘包了）、`trpg_dice_record` 与 `dice.log`（骰点是短线，不入档）、`secrets/`（KP 是真人）。
> **工具总数：7 个**（开团 / 回现场 / 线索三件套 / 角色卡两件套 / NPC / 时间线）。

## 四、回合流程（硬性顺序，★ 全篇最重要的一节）

跑团是**一来一回**，不是一个模型自己在写小说。鱼鱼的每一步都必须卡在这个流程里：

```
① KP 描述场景
        ↓
② 鱼鱼 RP：说自己做什么、说什么（哪怕只有半句话：「我蹲下来看那道划痕」）
        ↓
③ 鱼鱼请求骰点：「KP，我能掷个侦查吗？」   ← 必须问，不能自己掷
        ↓
④ KP 同意 → 骰娘掷骰 → 鱼鱼看到骰点数字
        ↓
⑤ ★ 等 KP 宣布结果（成功 / 失败 / 看到了什么）
        ↓
⑥ 鱼鱼 RP 结果反应 → 提出下一步行动
        ↓
     回到 ①
```

### 四条硬规矩

**1. 先 RP，再骰点。**

绝不允许「我要掷侦查」然后就掷了。必须先有一句角色动作或台词——**哪怕只有半句话**。

- ❌ 直接 `.ra侦查`
- ❌ 「我掷个侦查」（光说掷，没描述动作）
- ✅ 「我蹲下来，用手电贴着墙面照过去……」→ 这时才问能不能掷

**2. 骰点前先向 KP 寻求同意。**

KP 可能说「这个不用掷」「直接就能看到」，也可能说「掷吧」。不问就掷等于抢了 KP 的裁定权。

- ✅ 「KP，我可以掷侦查吗？」
- ❌ 自己 `.ra侦查`

**3. 能看到骰点，但绝不解读。**

骰点就在群里，看得见。但**绝不能自己算成败**——78 对她 65 的侦查算不算失败，轮不到她判断。

- ❌ 「78 > 65，我失败了」
- ✅ 看到数字，闭嘴，等 KP 说「你失败了」

**4. KP 宣布结果之后，才能继续 RP。**

结果没出来之前不许演后果。不许自己「我看到了」「我什么都没看到」——**半句话也不行**，那是抢戏。

### 为什么要这么严

| 乱掉哪一步 | 后果 |
|---|---|
| 先骰点再 RP | 变成按按钮的机器，群里没有画面感 |
| 不问就掷 | 抢 KP 的权力，KP 想说「不用掷」时很尴尬 |
| 自己解读骰点 | 和 KP 的宣布冲突，整场戏塌 |
| 结果没出就 RP | 她编了个结果，KP 说反了就得重演 |

### RP 的长度要求

**不限长度，但必须有。** 半句话也算（「我把手电筒往门缝里一照」），长一点更好（动作 + 语气 + 一点心理活动）。

唯一禁止的是：**零 RP 直接要骰点**。

## 五、发言格式（跑团时启用）

跑团时，一条消息必须能让人一眼分清三件事：**谁在说话 / 在做什么 / 谁在出戏**。

| 标记 | 含义 | 例子 |
|---|---|---|
| `""` | **角色说的话** | "你好，我……我叫娜塔莉娅，流亡的贵族" |
| `#` | **动作 / 描写** | #娜塔莉娅轻轻用手绞着裙子，似乎有些不安 |
| `（）` | **题外话（出戏 / OOC）** | （哇你们不觉得娜塔莉娅很可爱吗？） |

### 组合规则（两条）

**① 引号和 `#` 可以连用**（同一句里也行）：

```
#思考"我觉得，我们不能这么干呢。"
```

**② 但它们绝不能和括号出现在同一个气泡里。**

- ✅ 分两条发：
```
#她皱眉看了看门
（我周末可能不在）
```
- ❌ 混在一条里：
```
#她皱眉看了看门（我周末可能不在）
```

### ★ 强制：`""` 和 `#` 里不许写内心话、不许写补充说明

`""` 是**说出口的话**，`#` 是**别人看得见的动作**。这两样都是「展示到外面的」，
所以**内心活动、心理补充、旁白解释一律不许写进去**——在场的人根本不可能知道。

| ❌ 违规写法 | ✅ 改成能看见 / 能听见的 |
|---|---|
| #她心想这人真难缠，脸上却笑着 | #她笑了笑，眼睛没弯 |
| #他默默记下这个地址，决定明天一个人来 | #他盯着门牌看了两秒，掏出手机拍了一张 |
| #虽然有点怕，她还是推开了门，手在发抖 | #她握住门把，停了一下，才推开门 |
| "其实我早就怀疑他了"（角色并没说出来） | "我有个问题——你昨晚在哪？" |

**一句话判断标准**：

> 这句话 / 这个动作，**在场的人看得见或听得见吗**？看不见的，就不许写。

**想表达内心怎么办**：

1. **用外部表现暗示**——动作、表情、语气、停顿。这是演技，不是旁白。
2. **干脆说出口**——台词本身就是角色表达自己的合法途径（只是别太直白，真人不会把心事全说出来）。
3. **确实要让玩家知道的**，放 `（）` 里——那是出戏，不是角色的视角，不能混进 `#` / `""`。
### 括号的宽松写法

**可以只打前括号、不打后括号**：

```
（哇你们不觉得娜塔莉娅很可爱吗
```

这也算 OOC，不用补右括号。

### 为什么要分这么细

| 混了会怎样 | 后果 |
|---|---|
| 台词不加引号 | 分不清这句是角色说的，还是玩家本人在说话 |
| 动作不加 `#` | 描写和台词糊成一团，读起来像小说，不是跑团 |
| OOC 混进台词气泡 | KP 分不清哪句是入戏、哪句是在问规则，容易答错对象 |

> **实现提示**：这套格式必须写进 preset（每轮都要看到），不是写进人设卡。
> 验收方式：让她跑三轮，看有没有把 `（）` 和台词塞进同一条消息。

## 六、三个真难点

### 1. 假线索是 CoC 的灵魂

见 `verified` / `status` 字段。另外：
- 线索卡**只能追加**，不能改写原文（改了就丢证据）
- 推翻线索用 `status: disproven` + 保留原文 + 记「为什么被推翻」

### 2. KP 的裁定要变成状态（且禁止自己解读骰点）

跑团真正的信息流是这样的：

```
鱼鱼说要侦查 → KP 让她掷 → 骰娘出 78 → KP 看值后宣布「你失败了」 → 鱼鱼记账
                                     ↑
                            这一段鱼鱼不参与
```

骰点是**判定的输入**，解读是 **KP 的职权**。玩家（鱼鱼）不该碰这两步。

#### ★ 反面例子（模型极易犯）

群里出现 `.ra侦查 → 78`，而她的侦查是 65。模型很容易自作主张：「78 > 65，我失败了」，
然后写一堆「我什么都没看到」。

如果 KP 实际上说「你找到了」，那就彻底矛盾了——她会固执地坚持「我失败了」，把整个团带沟里。

所以必须立硬规矩：

> **看到骰娘结果时，把它当“只给 KP 看的数字”：自己不算、不宣布、不入档。等 KP 开口。**

#### 听到 KP 的话之后，往哪落

| KP 说 | 鱼鱼做什么 |
|---|---|
| 「你发现了 / 看到了 / 找到了……」 | `trpg_clue_add`（新线索，默认 `unverified`） |
| 「你什么也没发现」 | 什么都不记（没发生就是没发生） |
| 「你掉 3 点 SAN / 你受伤了」 | `trpg_char_patch` 改 `current.SAN` / `current.HP` |
| 「你们进入了…… / 天亮了 / 他走了」 | `trpg_timeline_add` 记一句场景推进 |
| 「他看起来在撒谎」（KP 给的心理暗示） | `trpg_npc_add` 或 `trpg_clue_add(verified=false)` |

### 3. 200 条重启 —— `trpg_state` 才是真核心

跑团四小时，上下文必然爆。所以每次重启后鱼鱼要能**三秒内回到现场**。
`trpg_state` 的输出必须信息密度极高，建议格式：

```
【当前】第二夜 · 废弃医院三楼（KP: 老张）
【我是】鱼鱼（记者）HP 9/11  SAN 46/55  状态：左臂擦伤
【手上的线索】
  · 已验证：护士说三楼封了（证据：门牌）
  · 未验证：管理员听到地下室有声（来源：NPC管理员）
  · 已推翻：酒保说箱子是药（实际是标本瓶）
【最近发生】
  · 20:14 我们在楼梯口遇到管理员，他拒绝让我们上去
  · 20:31 队里的阿蓝在图书馆翻了三小时，一无所得
  · 20:40 我在墙上发现了划痕
【未解决】谁在夜里搬东西 / 地下室的钥匙在哪
```

这份快照要能**直接贴在提示词里**，让模型一读就知道演到哪了。

## 七、跟现有系统的接线

```
群消息 ──► qq-bridge ──► DSH ──► MCP 工具
                                    │
                    ┌───────────────┼───────────────┐
                    ▼               ▼               ▼
              snowluma(QQ)     memory(日常)     trpg(跑团) ← 新增
```

- **新增一个 MCP server**：`src/trpg/mcp-server.mjs`，挂进 `cordis.patch.yml`（跟 memory 一样由 `setup-dsh.mjs` 托管）
- **读写都走 MCP**：跑团数据只有这个插件碰，桥接不碰，没有双写冲突
- **preset 加一节**：告诉鱼鱼「听到线索先记、骰娘掷完要记账、被唤醒先调 `trpg_state`」
- **人设层面**：跑团时她的语气应该跟着角色卡走（恐怖团不能用平时那只黏人鲸鱼的语气）

## 九、还剩一个开放问题

**鱼鱼怎么知道“骰娘掷了”？** 两个方案：
1. **靠它自己看**：骰娘结果作为群消息进来，它读到就判断「成没成」，把后果落到角色卡/线索/时间线。简单，但可能漏。
2. **桥上拦截**：桥接监听骰娘消息（识别 `.ra` / `.r` 的返回格式），自动把结论写进时间线。可靠，但要改 bridge.js。

> 这里讨论的是**结论会不会漏**，不是骰点会不会丢——骰点天生就是短线的，丢了无所谓。

建议先做 1，漏了再补 2。

## 十、实现记录（2026-10-27）

### 落地的文件

| 文件 | 作用 |
|---|---|
| `src/trpg/store.mjs` | 持久层：团 / 线索 / 角色卡 / 时间线 / NPC + `buildSnapshot()` |
| `src/trpg/mcp-server.mjs` | MCP 工具面（stdio），13 个工具 |
| `scripts/test-trpg-store.mjs` | 存储层单测（10 项，含坏 JSON 隔离、强制 source/reason） |
| `scripts/test-trpg-mcp.mjs` | 工具面冒烟（真的拉起 server 调一遍） |
| `scripts/probe-trpg-tools.mjs` | 端到端：用 `qq-chat-trpg` preset 建会话，验证模型真的能调 `mcp__trpg__*` |

### 与设计稿的差异（都是实现时才发现必须的）

1. **存储用 JSON 而不是 md**：`clues.json` / `timeline.json` / `npcs.json` / `chars/<角色>.json`。
   线索要按 id 精确标记、要按来源/场景/状态过滤，markdown 解析太脆；人可读性由 `trpg_state` 的快照输出兜住。
2. **多了三个工具**：`trpg_scene_set`（否则「当前场景」永远停在开场）、`trpg_char_new`（车卡，否则只能手改文件）、
   `trpg_stats`（排查「它怎么不记得」时先看这个）。
3. **角色卡改动必须带 `reason`**，线索必须带 `source`——这两条在工具层硬拒，不是靠提示词求模型自觉。

### 13 个工具

```
trpg_new        开团 / 合并已有团（并设为当前团）
trpg_state      ★回现场：场景 + HP/SAN + 线索分布 + 最近事件 + 未解决，≤800 字
trpg_scene_set  切场景 / 游戏内时间 / 未解决疑问
trpg_clue_add   记线索（source 必填，默认未验证）
trpg_clue_find  按关键词/来源/场景/状态查
trpg_clue_mark  证实 / 推翻 / 存疑（原文不改，只加标记）
trpg_char_new   车卡（属性/技能/物品/派生值）
trpg_char_show  读角色卡
trpg_char_patch 增量改 HP/MP/SAN/MOV（reason 必填）
trpg_timeline_add  记事件（只记结论）
trpg_npc_add    记 NPC（同名累加笔记）
trpg_npc_get    查 NPC
trpg_stats      档案规模统计
```
